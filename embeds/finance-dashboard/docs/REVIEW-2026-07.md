# Code review — 2026-07-25

Findings from a full review of the split app (`fd-*.js`, `fd-styles.css`, both shells),
exercised in a browser against the dev server on port 3134. All eight were reproduced or
measured, not inferred. **None are fixed** unless the status says otherwise.

Worst first. Line references were accurate at the time of review.

---

## 1. "fd-data.js is the only file that changes to go live" is not true

**Severity: high — it invalidates the build estimate, not just a line of code.**

`docs/DATA-REQUIREMENTS.md` §1 commits to "aggregate in SQL, the browser never loads a
payment row it isn't showing", and §2 lists the KPI figures and the by-type chart as
"derived in the browser" from summary *columns*. Four renderers derive them from
`run.txns` instead.

Verified by simulating the live shape (set `run.stats`, `delete run.txns`) and re-running
each renderer:

| Renderer | Result |
|---|---|
| `renderRuns` | OK — goes through `runStats` |
| `renderTrend` | OK — goes through `runStats` |
| `renderKpis` | **throws** — `Cannot read properties of undefined (reading 'status')` |
| `renderTypeBars` | **throws** — reading `'type'` |
| `renderDeclinesTable` | **throws** — reading `'filter'` |
| `FDRun.renderDetail` | **throws** — reading `'filter'` |

Sites: `fd-dashboard.js:118` (`runs.flatMap(r => r.txns)`), `:245`, `:441`; and
`fd-run.js:141` / `:155` / `:161`.

`runStats()` short-circuits on `run.stats` correctly — these four bypass it entirely. Build
order step 3 ("Nothing else in the app changes") will fail on the first live load. The SQL
columns needed are already specified in §2 (the `DDCount`/`DDValue` set and the
`{Type}OkCount` recommendation), so this is view-layer work the plan currently budgets zero
time for.

**Fix:** point those four at summary columns, and correct the claim in `README.md` and the
`fd-data.js` header.

## 2. `esc()` is used in JS-string contexts, where it isn't safe

**Severity: high once live — currently dormant.**

`esc()` (`fd-core.js:77`) escapes `& < > "` but **not** `'`. Three templates interpolate
`esc()`'d data into a single-quoted JS string inside an `onclick` attribute. Verified:

```
esc("O'Brien');window.__FD_PWNED=1;//")
  → onclick="FD.openRun('O'Brien');window.__FD_PWNED=1;//')"
```

Sites: `fd-dashboard.js:388` and `:524` (`run.id`), `:528` (`t.ref`).

Dormant today because mock ids are `RUN-2230` / `PMT-123456`. It goes live the moment
`BatchRef` / `PaymentRef` come from iMIS, where an apostrophe in a reference or batch name
is ordinary — then it's stored XSS in a finance-role page rendering member data.

`fd-dashboard.js:493` **does** guard it (`.replace(/'/g, "\\'")`), so the hazard was known
at one call site and missed at three.

**Fix:** move these to `data-` attributes with a delegated listener, as the run-card
keyboard handler already does. Patching each call site is the weaker option.

## 3. Deploying publishes the internal docs

**Severity: medium-high — one-line fix, embarrassing if missed.**

Output directory is `/` with no exclusions, so every root file becomes a public,
unauthenticated URL on `hubfinancedashboard.pages.dev`. Confirmed against the static server
(same behaviour as Pages):

```
Payment%20runs.docx          HTTP 200  16930 bytes
docs/DATA-REQUIREMENTS.md    HTTP 200  16392 bytes
Payment%20Run%20Screen.html  HTTP 200  1200889 bytes
```

That publishes internal notes on iMIS payment-status semantics, the full SQL-view and
CloudToolz endpoint design, §9's candid note that `licensedHosts` is not a data control,
and 1.4 MB of superseded mockups.

**Fix:** add a deploy step keeping docs and the artifact mockups out of the published root.

## 4. Half the runs can't show their transactions past row 100

**Severity: medium — a functional dead end.**

`detailState.page` exists and `loadTransactions` pages correctly, but **nothing ever
increments it** — there is no pager control. On RUN-2230 (319 transactions): 100 rows, and
the note "use Export CSV for the full list" — where Export CSV is
`FD.toast('CSV export queued (mock)')`.

**98 of 192 mock runs exceed 100 transactions**; the largest is 995. So on ~51% of runs the
remaining rows are unreachable by any route.

§7 anticipates "Run: … next page", so the gap is known, but it isn't in the README status
section or the build order and should be.

## 5. Two KPI cards claim to be buttons but aren't keyboard-operable

**Severity: medium — accessibility.**

`fd-dashboard.js:153` emits `role="button" tabindex="0" onclick=…` for the Declined and
Runs-to-review cards. Focusing one and dispatching Enter does nothing: `fd-boot.js`'s
Enter/Space handler only matches `.run-card-5c`. Both cards take focus, announce themselves
as buttons to a screen reader, and don't activate.

**Fix:** widen the selector in `fd-boot.js:61` — the pattern to copy is already there.

## 6. Range switch contradicts the review filter

**Severity: low-medium — reads as a bug to a user.**

Click "To review", then switch to Last 7 days: the chip reads **"To review 0"** while its
own filter displays 2 runs, from **10 and 28 days ago**, under a header saying "Last 7
days". `FD.setRange` (`fd-dashboard.js:44`) doesn't reconcile `state.longProc`.

The notice does say "across all dates", which softens it, but an active chip badged 0
showing 2 results is contradictory.

## 7. Trend chart stacks bars against a non-stacked maximum

**Severity: low — but see the note below.**

`max` comes from collected only (`fd-dashboard.js:203`) while the declined bar is stacked on
top (`:210`). So the peak collected day overflows the 112px plot area by `bad/max × 112`
whenever it has **any** declines.

Measured with ~20% of the peak day flipped to Declined: bars totalled **113.3px against a
112px plot area**, rising above the `$36,980` y-axis label that claims to be the top. It
only clips off the SVG past roughly 16% declines-by-value on the peak day, so realistic
data stays inside the 18px headroom.

**Note for Hub Widgets:** this is the exact trap the vertical-bar widget must not inherit —
see `Claude/Hub Widgets/docs/PLAN.md` §10, "single series or stacked".

## 8. `staggerRuns` leaks a dead listener

**Severity: trivial.**

`fd-dashboard.js:325` attaches an `animationend` listener to `#runs-list` on every filter
change whose body only removes itself. Under `prefers-reduced-motion` the list's own
animation is `none`, so it never fires and they accumulate. Dead code either way — drop it.

## Not a problem: performance

Recorded so nobody optimises it speculatively. Measured on the 90-day mock set:

| | |
|---|---|
| 5 keystrokes in the declines search, 34,472 transactions scanned each | **53ms total** |
| Full 90-day dashboard render | **24ms** |
| Console errors across all filters, ranges, both surfaces, deep links | **none** |

The two slow calls seen in unrelated network testing were the browser's
six-connections-per-host limit, not application cost.

## What was verified as working

Worth stating, because the review found the codebase in good shape overall:

- **CSS scoping is airtight.** A grep for unscoped selectors returns zero; every rule sits
  under `.fd-root` and tokens are on `.fd-root`, not `:root`.
- **`runStats`/`runState` really are the single source of run-level figures**, so the list,
  the KPI cards and the run screen cannot disagree.
- **Two-surface navigation works**, including deep links: `?fdrun=RUN-2230` resolved to the
  same run on a cold page load, confirming the deterministic-seed design.
- `docs/DATA-REQUIREMENTS.md` is unusually good — better than most production API designs.
