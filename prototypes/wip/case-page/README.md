## Problem

The Manage Case page in iMIS (`/Cases_ManageCase?CaseID=C217&CaseNum=214`;
content record `@/_i4u_/Core/Cases/Layouts/Manage-Case`) was built before the
UnionSuite theme. Its header is a plain block: the reference and title, the
case date, the description, then a Details list (Status, Type, Subtype,
Priority, Primary contact, Lead staff, Last activity, Last activity on/by).
Below it are horizontal tabs: Notes & Attachments, Tasks, Meetings, Contacts,
Summary (the case history), Expenses and Resolution.

This folder rebuilds the page from the shared theme. It starts from the
agreement page (`../agreement-page/`, layout v2): a case is like an agreement
with less on it (owner, 8 October 2026).

## What a case holds (owner, 8 October 2026)

- Notes, attachments and tasks.
- Emails, both incoming and outgoing.
- Parties: usually one member, sometimes several members, sometimes
  employers.
- Staff: each has a role and a type. A delegate or member representative is
  sometimes assigned to help.
- Resolution.
- Meetings: on the current page, so kept.
- Expenses: dev only, so left out for now.
- Member alerts on the case, for a member party who:
  - is unfinancial,
  - is no longer a member, or
  - joined within the last three months.

## Preview

Start `static-node` from `.claude/launch.json` (port 8778) and open:

```text
http://localhost:8778/prototypes/wip/case-page/index.html
```

For a single file that opens from disk with no server (to share or
review), run `node prototypes/wip/case-page/build-standalone.cjs`: it writes
`Case-Page-Standalone.html` (about 7.6 MiB, ignored by Git) with every
stylesheet, script, font and template inlined. `--check` reports a stale
copy; rebuild after any change.

The page itself must be served, because it fetches the templates in `templates/`
and fills their `{#query.Field}` tokens. If a sample row is missing a field
the template uses, rendering stops with an error.

Toolbar (prototype only). The variant buttons switch in place: each one
updates the address (so a reload or a shared link keeps it), rebuilds the
sample data and re-renders the page, with no reload.

| Control | Effect |
| --- | --- |
| Member: unfinancial / financial / new / former | `?member=`: the member's standing. It changes the badge on the banner's member line, the warning on the member card and the party badge. A financial member has no warning. |
| Jobs: current job / former job / no workplace / not chosen / 1 | Priya's jobs (C42): two current and one former. The case on the night shift (the default): the Work label opens the menu, "2 current · 1 former" at the end of its rule, and the group opens with Current and "Since Mar 2020". `?jobs=former`: the case on the former job, Former and "Worked there Mar 2016 – Jan 2019". `?jobs=none`: not about a workplace (0). `?jobs=unset`: none chosen, so the card asks "Which job is this case about?". `?jobs=single`: one job, the case on it. |
| Case: larger / new / typical | Larger (the default, so every panel has something to show; owner, 8 October 2026): three parties and an employer, an organiser and a delegate besides the lead. `?size=new`: a case opened today with nothing recorded, so every list shows its empty state (C13). `?size=typical`: the usual case, one member and one staff member. |
| Age: recent / older | `?age=older`: opened 2 July, so the banner reads "98 days", and the last contact with the member was 21 days ago (amber, C18). |
| Lead staff: assigned / none | `?lead=none`: the banner's Lead staff fact reads "No lead staff assigned" in red, as the current page does. |
| Status: open / closed | `?case=closed`: the status is Closed, the Overview leads with the resolution, and the banner's Actions offer Edit resolution and Reopen case. Resolve case and Reopen case also change it, as the real saves would (C16). |

## Layout

Reworked on 8 October 2026 after the owner's review: the first version spent
the Overview on party and staff tiles. Most cases are worked by one
staff member for one member, so the Overview now answers, in order: what
the case is (banner), who the member is and whether the union can act for
them (member card), what to do next (tasks, next meeting) and what happened
last (recent activity).

## Open decisions

1. **Popup pages.** Every `Cases_*` URL in the case actions (`ActionDefinitions.js`) is a
   placeholder that follows the agreement pattern. It needs the real case
   editor, note, task, meeting, contact, staff and attachment pages.
2. **Member standing rules.** Which iMIS fields mark unfinancial
   (paid-through date?), no longer a member (status?) and joined (join date).
   If a member matches two (new and unfinancial), the most serious shows.
3. **Endpoints and pages still to build** (owner's exports, 28 October
   2026; the built ones are listed in HANDOVER.md → Live build).
   `/cases/quick-add/contact` (a stub today; its replacement is drafted in
   `flows/`); the workplace save's corrected flow (C42, also in `flows/`),
   and `set-primary-party` setting the new primary's primary workplace or
   clearing it (C42); `/cases/attachment-access` and
   `/cases/reopen` (CloudToolz). `/cases/resolve-case` exists but has not
   run; the Resolve case form (`/Cases_ResolveCase`) is to confirm. Can an
   employer be the primary party? The prototype says no.
4. **Member card fields.** The suggested details (mobile, email, paid to,
   joined, employer, workplace, classification, delegate) are a starting
   point; the IQA's columns decide them.
5. **Incoming emails.** Where they are stored (the "Logged Email" file tag
   suggests they are logged as files), and whether this panel needs a "Log
   email" or "Send email" action.
6. **History.** Decided (owner, 25 October 2026): the change history's
   Details view is the History log, a Query Menu on `i4u_UT_Logging` (one
   row per field) with the native Export, below the Changes iPart
   (`us-activity-detail us-activity-detail-history`); the toggle comes from
   `us-details-view-history` in the `us-case-changes` preset
   (`US-DETAILS-VIEW`, guide `#change-history-details`).
7. **Task saving.** Whether `/ca/complete-task` saves case tasks. Both are
   `Zen_CloudFiles_Notes` rows, but this hasn't been confirmed.
8. **Case statuses.** The full list, to set each status tone. New, Open and
   In progress are amber; Closed is neutral.
9. **Access.** The live page has a "No Access to Case" layout
   (`Case Layout - No Access to Case`). The prototype doesn't show the
   no-access state yet. On load, the manage case page asks CloudToolz
   `POST /cases/case-access` with `{"CaseOrdinal"}` (the CaseNum; owner,
   27 October 2026: the "Cases: Case Access Check" Flowz), checked as
   `/ca/note-access` is, answering `{"Access": "Granted" |
   "Restricted", "MemberID"}` (MemberID is the case's
   `PrimaryContactID`). Restricted replaces the page with
   `/UTNewTheme/Cases_NoAccess?CaseID=&CaseNum=&ID=<MemberID>`
   (`noAccessPage` in `ActionDefinitions.js`; its placeholder content is
   `templates/Case-No-Access-Content-HTML.html`, whose Back to member
   button is `cases.back-to-member`, opening `/UTNewTheme/Party.aspx?ID=`). A failed
   check or any other answer stays on the page and logs a warning. While
   the check runs, `US-CASE-ACCESS` (`zUnionSuite.css`) hides the page's
   `.main` (page CSS class `us-case-page`) from first paint; granted or
   failed fades it in, and with no answer at all it shows after 15
   seconds. The redirect only hides the page: the case's IQAs and
   endpoints must still refuse a user without access.
10. **Expenses.** Left out while it is dev only.
11. **Case details fields.** The Details tab's columns (case, workplace,
    dates, tags, description) are a starting point; which fields does the
    case hold, and which can staff edit?
12. **Resolve case form.** Which fields it asks for, which are required,
    and whether resolving should also complete or cancel the open tasks
